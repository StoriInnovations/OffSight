# Chasing OffSight's grey frames past the format

> **Resolution (12 Oct 2026, confirmed on the test Mac).** The cause was macOS video effects, which apply per app to every camera, virtual ones included, and blanked the artwork. Photographs survived them; the dark, flat artwork did not. Apple's media engineering states that effects only apply to video smaller than 1920×1440 ([forum thread 805786](https://developer.apple.com/forums/thread/805786)). OffSight Camera now advertises the camera's size scaled up, keeping its shape, to at least 1920×1440 (2560×1440 for a 1080p camera). With that, the default placeholder displays in Photo Booth and Teams. Effects for live video are applied on OffSight's own capture instead. The analysis below predates this finding and is kept as the record.

OffSight's grey placeholder is almost certainly not caused by its pixel format, pool or format description. Every working CoreMediaIO camera extension that could be inspected uses the same settings: Apple's Xcode template, OBS Studio 30+, Laurent Denoue's sample, Halle Winkler's samples, ptpwebcam, SimulatorCamera and jcm93/Record. They all advertise a single 32BGRA format with `extensions: nil`, use an IOSurface pool with empty properties, and set no colour attachments. Their synthetic frames display in Photo Booth, and OBS's display in meeting apps. In OffSight's current implementation, the live frames that do display go through the same send code, timing construction, pool type and attachment stripping as the placeholders. So whatever turns placeholders grey depends on the frame's **content** or **cadence**, not on how the frame is wrapped. Only two documented mechanisms make Photo Booth show nothing while QuickTime shows frames. The first is the client-side CMIO video synchronizer, which drops frames whose timestamps arrive "too quickly". The second is wrong sample timing, which Photo Booth punishes and QuickTime tolerates. Neither fully explains a failure that hits every synthetic pattern but no live frame. The research also turns up an untested, content-dependent explanation that fits all of OffSight's observations: system or in-app camera effects that segment people, acting on frames with no person in them. The fastest route to an answer is about an hour of diagnostics. Capture the consumer-side CMIO log, turn off every video effect, then run a 2×2 experiment that swaps content and cadence between the live and placeholder paths. Only after that should OffSight start format work (420v, continuous frame-rate ranges), which is worth doing anyway for Catalyst-based clients.

## Every working camera extension ships OffSight's format

Apple's template, which WWDC22 session 10022 demonstrates as a "horizontal white line that moves up and down the frame at 60 frames per second", builds one 1920×1080 `kCVPixelFormatType_32BGRA` format description with `extensions: nil` ([WWDC22 10022](https://developer.apple.com/videos/play/wwdc2022/10022/)). It allocates from a pool whose only IOSurface setting is `kCVPixelBufferIOSurfacePropertiesKey: [:]`, with an allocation threshold of 5. On each timer tick it memsets a fresh buffer to zero, which is black with **alpha 0**, and writes white `0xFFFFFFFF` rows. It stamps PTS with `CMClockGetTime(CMClockGetHostTimeClock())`, leaves duration and DTS invalid, and sends with `discontinuity: []` and `hostTimeInNanoseconds = PTS.seconds × 1e9` ([below/WWDC22_CoreMediaIO](https://github.com/below/WWDC22_CoreMediaIO/blob/main/Extension/ExtensionProvider.swift)). The template's timer interval is written `Double(1/kFrameRate)` with an integer `kFrameRate`, so it evaluates to zero and the timer fires far faster than 60 Hz. Unmodified template output is still reported to display in Photo Booth ([ptpwebcam PORTING_STATUS.md](https://github.com/dognotdog/ptpwebcam/blob/master/PORTING_STATUS.md); [Apple Developer Forums 706184](https://developer.apple.com/forums/thread/706184)). Photo Booth therefore accepts synthetic frames, transparent alpha and an over-rate sender.

OBS Studio's macOS virtual camera is the most widely used production reference, and it is nearly a copy of the template. It uses one BGRA 1920×1080 format with min = max frame duration of 1/60 and `validFrameDurations: nil`, the same IOSurface pool with threshold 5, and a `.strict` zero-leeway timer that redraws a bundled PNG into a fresh pool buffer every tick. Its PTS comes from the host clock and its `hostTimeInNanoseconds` is derived from that PTS ([OBSCameraDeviceSource.swift](https://github.com/obsproject/obs-studio/blob/master/plugins/mac-virtualcam/src/camera-extension/OBSCameraDeviceSource.swift)). Two OBS behaviours matter for OffSight. First, the placeholder timer returns immediately once `sinkStarted` is true, so placeholder and relayed frames never interleave. Second, relayed sink frames are forwarded as-is: they keep the producer's PTS and format description, and are usually NV12 or UYVY at OBS's output size, not the advertised BGRA 1080p ([OBS plugin-main.mm](https://github.com/obsproject/obs-studio/blob/master/plugins/mac-virtualcam/src/obs-plugin/plugin-main.mm); [obs-studio#13559](https://github.com/obsproject/obs-studio/issues/13559)). Denoue's sample, on which the OBS code is visibly based, draws black plus a seconds counter each frame and uses the same `sinkStarted` gate ([ldenoue cameraextensionProvider.swift](https://github.com/ldenoue/cameraextension/blob/main/cameraextension/cameraextensionProvider.swift)). Halle Winkler's samples go further. One sends a 32ARGB buffer that is not from a pool, and another sends 2vuy, both under a BGRA advertisement ([Halle/TechnicalDifficulties](https://github.com/Halle/TechnicalDifficulties/blob/main/Extension/ExtensionProvider.swift); [Halle/ArtFilm](https://github.com/Halle/ArtFilm/blob/main/Extension/ExtensionProvider.swift)). A grep across eight such codebases found **no colour-primaries, transfer-function or YCbCr-matrix attachments anywhere** ([ldenoue](https://github.com/ldenoue/cameraextension); [jcm93/Record](https://github.com/jcm93/Record/blob/main/RecordCameraExtension/RecordCameraExtensionProvider.swift); [SimulatorCamera](https://github.com/dautovri/SimulatorCamera/blob/main/SimulatorCameraExtension/SimulatorCameraProvider.swift)).

| Aspect | Apple template | OBS 30+ | ldenoue / Screegle | OffSight's current implementation |
|---|---|---|---|---|
| Advertised format | 32BGRA 1920×1080, `extensions: nil` | Same, 60 fps | 32BGRA, 30 fps | 32BGRA 1920×1080, `extensions: nil`, 30 fps |
| Pool | IOSurface `[:]`, threshold 5 | Same | Same | IOSurface-backed, min buffer count 4 |
| Placeholder content | Alpha-0 black + white stripe, drawn each tick | PNG redrawn each tick (`noneSkipFirst`) | Black + text + seconds counter | Pre-rendered master copied row by row (alpha 255); app path: VT copy + one nudged pixel |
| Sample duration | Invalid | Invalid | Invalid | 1/30 |
| `hostTimeInNanoseconds` | PTS × 1e9 | PTS × 1e9 | PTS × 1e9 | Separate host-clock read, microseconds after PTS |
| Placeholder vs relay | No sink | Hard gate on `sinkStarted` | Hard gate on `sinkStarted` | Sends if no sink frame in the last 0.1 s |
| Relayed frames | No relay | Forwarded unchanged, producer PTS | Forwarded unchanged | Re-wrapped with fresh host timing and the advertised description |

The commercial field has converged on the same architecture without publishing its internals. Since macOS 14.1, Apple supports only cameras built on modern system extensions. Restoring legacy DAL support also disables the menu-bar camera privacy indicator for those devices ([Apple Support HT213969](https://support.apple.com/HT213969)), which rules out DAL for a privacy product. Camo, Airtime, Ecamm Live, Elgato Camera Hub and NDI Virtual Input all now install camera extensions that users approve under Login Items & Extensions ([Camo release notes](https://camo.com/support/camo/release-notes?b=20240102); [Ecamm support](https://support.ecamm.com/en/articles/3824881-virtual-camera-doesn-t-show-up-in-apps); [Elgato Sequoia article](https://help.elgato.com/hc/en-us/articles/30069817477777-Elgato-Camera-Hub-How-to-enable-Virtual-Camera-on-macOS-15-Sequoia); [NDI Virtual Input](https://docs.ndi.video/all/using-ndi/ndi-tools/ndi-tools-for-mac/virtual-input)). Snap Camera, CamTwist, EpocCam and Logi Capture stayed on DAL and died ([TechRadar](https://www.techradar.com/news/snap-is-closing-its-zoom-video-filter-tool); [Elgato EpocCam guide](https://help.elgato.com/hc/en-us/articles/360051151552-EpocCam-macOS-Setup-Guide)). No vendor documents its advertised formats or idle-frame cadence. Camo says only that it shows on-screen status text when paused or when Camo Studio is not running ([Camo FAQ](https://camo.com/support/camo/camo-faq)). Vendors do hit client-specific rendering bugs. Elgato Camera Hub 2.0, for example, fixed "green virtual camera output in Zoom on macOS" without saying why ([Camera Hub 2.0 notes](https://help.elgato.com/hc/en-us/articles/34177528821265-Elgato-Camera-Hub-2-0-Release-Notes)). OffSight's design (a source stream plus a sink stream, the app relaying live frames, an in-extension fallback placeholder) is mainstream. Its format choices match the reference that ships to millions of users.

## Consumers validate, pace and convert what QuickTime shows raw

The API contract is thin. Apple's header says `hostTimeInNanoseconds` is "the host time in nanoseconds when the buffer was captured". Sample-buffer timestamps "should be relative to the clock timebase specified with clockType", and samples go only to clients whose authorization status is authorized ([CMIOExtensionStream.h](https://raw.githubusercontent.com/alexey-lysiuk/macos-sdk/main/MacOSX14.5.sdk/System/Library/Frameworks/CoreMediaIO.framework/Versions/A/Headers/CMIOExtensionStream.h)). WWDC adds that "all the buffers your extension provides are validated before being delivered to an app". It does not list the validation rules ([WWDC22 10022](https://developer.apple.com/videos/play/wwdc2022/10022/)). No Apple source says what happens when `hostTimeInNanoseconds` and PTS disagree.

What the developer community has established empirically is that **timing is the only proven cause of a Photo Booth blank screen** in the camera-extension era. In thread 725481, a developer whose source-plus-sink extension showed a blank Photo Booth first blamed 420v. They then reported "the pixel format was not the issue… I wasn't setting the timing info right". The fix re-stamped every buffer with `CMSampleBufferCreateCopyWithNewTiming` using a host-clock PTS, and a second developer confirmed they had been passing the client app's timing through unchanged ([Apple Developer Forums 725481](https://developer.apple.com/forums/thread/725481)). Thread 726417 exposes the mechanism. Client-side logs from `CMIO_Unit_Synchronizer_Video.cpp` read `SyncUsingIntegralFrameTiming observing getting frames too quickly by a lot … dropping this frame`, and CMIO logged "creating discontinuity because the timebase jumped" even though the extension passed no discontinuity flag. Re-stamping timing stopped the drops ([Apple Developer Forums 726417](https://developer.apple.com/forums/thread/726417)). The same synchronizer messages appear in QuickTime logs for a laggy physical camera ([Apple Community 251375319](https://discussions.apple.com/thread/251375319)), so the unit lives in the client's capture graph, and how strictly it is applied evidently varies by client. QuickTime is not immune either: the unmodified template's preview freezes after a while in QuickTime, and changing the discontinuity flags did not help ([Apple Developer Forums 761771](https://developer.apple.com/forums/thread/761771)).

Pixel format matters less than intuition suggests, with one notable exception. The 725481 author found that Photo Booth accepts either 420v or BGRA in `.formats` and renders buffers that differ from the declared format. QuickTime accepts only BGRA in `.formats` but also renders 420v buffers ([Apple Developer Forums 725481](https://developer.apple.com/forums/thread/725481)). Converting clients still do real work on BGRA, though. Chromium's AVFoundation capturer recognises only 420f, 420v, 2vuy, yuvs and dmb1. It ignores a BGRA format as "unknown FourCC" and asks AVFoundation to scale and convert every frame to 420v through `videoSettings` ([Chromium video_capture_device_avfoundation.mm](https://raw.githubusercontent.com/chromium/chromium/main/media/capture/video/apple/video_capture_device_avfoundation.mm)). Apple warns that BGRA "aren't native and require conversion" ([AVCaptureVideoDataOutput docs](https://developer.apple.com/documentation/avfoundation/avcapturevideodataoutput)). Whether new Teams on macOS captures through Chromium code or its own native stack is undocumented. The exception is Catalyst and FigCaptureSession clients. WhatsApp for Mac showed black for both a BGRA-only extension and OBS's camera, because graph building aborted with `err=-12780` right after the BGRA format was applied. Publishing 420v at three sizes with a continuous 1/60 s to 1 s frame-duration range fixed it, and so did using single-point frame rates, which had also made AVFoundation throw on 24 fps requests ([kortexa-ai/aicamera #71](https://github.com/kortexa-ai/aicamera/issues/71)). That failure blocks every frame, live or placeholder, so it is a different bug from OffSight's. It is still a reason to add 420v.

Several other mechanisms can starve a client silently. AVCaptureVideoDataOutput discards late frames by default ([alwaysDiscardsLateVideoFrames](https://developer.apple.com/documentation/avfoundation/avcapturevideodataoutput/alwaysdiscardslatevideoframes)). Clients such as Photo Booth hold sample buffers long enough to exhaust small pools, producing "Dropping 512 frames, because we're out of buffers" ([Apple Developer Forums 726416](https://developer.apple.com/forums/thread/726416)). CMIO also defines a per-stream "no data" timeout, after which a device is considered to be in a period of no data ([CMIOHardwareStream.h](https://raw.githubusercontent.com/alexey-lysiuk/macos-sdk/main/MacOSX14.5.sdk/System/Library/Frameworks/CoreMediaIO.framework/Versions/A/Headers/CMIOHardwareStream.h)). A client that sees no deliverable frames for long enough would plausibly fall back to its own empty surface. Because of this, **OffSight's flat mid-grey test pattern proves nothing**: it cannot be told apart from Photo Booth's or Teams' own "no video" grey. Only the moving-bar result is evidence.

## Live frames share the send code, so content or cadence must differ

The key constraint comes from OffSight's own observations. Live and app-placeholder frames both cross the sink and are pulled by the same recursive `consumeSampleBuffer` loop. Both are re-wrapped with the same advertised format description, the same host-clock PTS, the same 1/30 duration and the same separately read `hostTimeInNanoseconds`. Both originate as VTPixelTransferSession copies into the same kind of IOSurface-backed pool buffer, with attachments removed. Yet live frames display everywhere and app placeholders display only in QuickTime. The extension's own fallback, which runs with the app not running and so has no second sender, fails the same way. Any hypothesis that blames the wrapper, the pool, attachments, IOSurface backing, alpha or the advertised format must explain why the identical wrapper works for live frames. None can. What genuinely differs between the two app paths is **what the pixels show** (a camera image of a person versus synthetic slate, bars or grey) and **when frames are produced** (camera-driven cadence versus a 30 Hz timer).

| Hypothesis | Evidence for | Weighed against OffSight's current implementation | Verdict |
|---|---|---|---|
| BGRA or no extensions rejected by Photo Booth/Teams | Catalyst clients need 420v ([aicamera #71](https://github.com/kortexa-ai/aicamera/issues/71)) | Live frames display under the same format; OBS ships it | Ruled out as the differentiator |
| Missing colour attachments | VideoToolbox can fail on RGB without colour info ([QA1839](https://developer.apple.com/library/archive/qa/qa1839/_index.html)) | Live frames are stripped identically | Ruled out as the differentiator |
| Non-IOSurface buffer, wrong alpha | IOSurface recommended ([forum 721710](https://developer.apple.com/forums/thread/721710)) | Both paths use IOSurface pools; template's alpha 0 works | Ruled out |
| Producer PTS forwarded | Proven Photo Booth blank ([forum 725481](https://developer.apple.com/forums/thread/725481)) | OffSight re-stamps every frame | Ruled out |
| Two senders interleaving | OBS gates hard on `sinkStarted` | Extension-only fallback (app not running) still fails | Cannot be the sole cause; still a transition risk |
| Synchronizer cadence drops | "Too quickly" drops documented ([forum 726417](https://developer.apple.com/forums/thread/726417)) | Same timing code as live; only send cadence differs; template's flood still displays | Open, needs the 2×2 test |
| Pool exhaustion or stale extension build | [forum 726416](https://developer.apple.com/forums/thread/726416); [broadify PR #221](https://github.com/pivotrecruiting/broadify-bridge/pull/221) | Counters show thousands of sends; live works on the same binary | Unlikely; cheap to exclude |
| Person-segmenting effects acting on person-free frames | macOS camera effects apply to all cameras, including virtual ones ([Airtime help](https://help.airtime.com/hc/en-us/articles/35745674133527)) | Explains content-dependence, per-app split and silent logs | Untested; check first |

The cadence hypothesis deserves serious attention because it is the only documented mechanism that discriminates between clients. OffSight's strict timer produces PTS deltas centred exactly on the advertised 1/30 s, and it attaches a valid 1/30 duration that no reference implementation sets. A synchronizer that runs "integral frame timing" could plausibly flag a meaningful fraction of jittered ticks as early. Camera-driven frames, which commonly arrive slightly slower or less regularly, would escape that check. The case against it is equally concrete: the template floods Photo Booth at an effectively unbounded rate and still shows its stripe. Excess frames get dropped, but some survive. Pure cadence drops would therefore produce stutter, not unbroken grey, unless OffSight's timing trips a stricter mode. That leaves the cadence hypothesis open, and only the consumer-side log can settle it.

The content hypothesis is the research's most interesting lead, though no source confirms it. Airtime documents that a macOS camera effect such as Portrait mode, once enabled in Zoom, Meet or Teams, is applied to every camera, including its virtual one. Turning effects off requires the Control Center video menu while the app is running ([Airtime help](https://help.airtime.com/hc/en-us/articles/35745674133527)). Effects that segment a person from the background, whether Apple's system effects or Teams' own background tools, have nothing to keep when the frame contains no person. A frame like that could plausibly come out as a uniform replacement surface. Such a mechanism would explain everything OffSight sees. Live frames containing the user display. Every synthetic pattern, including the moving bar, fails on whichever path it takes. QuickTime, with its own per-app effect state, is unaffected. The extension log shows no error, because nothing is wrong on the producer side. The research found no report tying grey output to segmentation on a camera extension, and no evidence that Photo Booth or Teams detect "static" frames. This is a hypothesis to falsify in five minutes, not a finding.

One more departure from the references is worth noting even though it cannot explain the live/placeholder split. A 2026 report on macOS 26.2 describes an extension that drew with NSImage/CGContext on a 60 fps timer. It logged "Invalid display 0x00000000" and degraded from jitter to a solid accent colour in Zoom and Meet ([Apple Developer Forums 817478](https://developer.apple.com/forums/thread/817478)). OffSight's fallback renders its master once with plain CGContext and copies bytes after that, which avoids that pattern. The log string is still worth a grep.

## Recommendations: diagnose in an hour, then fix, then rethink

### Diagnostics that separate the hypotheses

Run these in order. Each step is cheap, and the first three decide which branch of the fixes applies.

| Priority | Diagnostic | What it decides |
|---|---|---|
| 1 | With Photo Booth and then Teams showing OffSight, open the Control Center video menu and turn off Portrait, Studio Light, background and every other effect. Also set Teams' own background effect to none. Retest the moving bar. Then point the live camera at an empty wall, and separately put a photo of a face into the placeholder master. | If the placeholder appears with effects off, or the face-bearing placeholder displays while the empty-wall live feed goes grey, the cause is content segmentation, not CMIO. |
| 2 | Capture the consumer side while the moving-bar placeholder runs: `log stream --level debug --predicate 'subsystem == "com.apple.cmio" OR subsystem == "com.apple.coremedia"'`, the predicates OverSight uses ([OverSight AVMonitor.m](https://github.com/objective-see/OverSight/blob/master/Application/Application/AVMonitor.m)). Filter for `Synchronizer`, `too quickly`, `timebase jumped`, `out of buffers`, `Dropping`, `-12780` and `Invalid display`, in the Photo Booth process and in registerassistantservice. | Synchronizer drop lines confirm the cadence/timing branch. Silence while frames are being sent points away from CMIO pacing. |
| 3 | Switch from live to placeholder while Photo Booth is open and watch the transition. | A frozen last live frame that turns grey only after a delay means frames are being dropped (synchronizer or no-data timeout). An instant switch to grey means frames are arriving and being rendered as grey. |
| 4 | Run a 2×2 content × cadence experiment. Send the latest *live* frame from the extension's strict 30 Hz timer, and send the *placeholder* once per arriving camera frame. | Shows whether the failure follows the pixels or the clock. |
| 5 | Paste the template's loop verbatim into OffSight's fallback: alpha-0 black, white stripe, duration invalid, `hostTimeInNanoseconds` = PTS × 1e9. Then reintroduce OffSight's differences one at a time (duration 1/30, separate host read, custom source property, 30 Hz). | If the template frame displays inside OffSight's extension, the first difference that breaks it is the cause. |
| 6 | Write a minimal AVCaptureVideoDataOutput test client that requests 420v, as Chromium does, and logs received frames, PTS deltas and drop callbacks. Also run `systemextensionsctl list` to confirm the active build ([broadify PR #221](https://github.com/pivotrecruiting/broadify-bridge/pull/221)). | Gives a scriptable consumer that converts like Teams and Chrome, and excludes a stale extension. |

### Fixes that align OffSight with shipping code

Some changes cost almost nothing and remove every gratuitous difference from OBS and the template, so they belong in OffSight whatever the diagnostics show. Derive `hostTimeInNanoseconds` from the PTS value itself rather than from a second clock read. Leave sample duration and DTS invalid, as every reference does. Replace the 0.1 s "no recent sink frame" heuristic with a hard `sinkStarted`-style gate, or better, a single sending loop. That guarantees one strictly monotonic PTS timeline across live/placeholder transitions, which the synchronizer evidence says clients depend on ([Apple Developer Forums 726417](https://developer.apple.com/forums/thread/726417)). Remove the custom read-only property from the source stream for the A/B test. If the problem persists, check every `CVPixelBufferPoolCreatePixelBuffer` and `CMSampleBufferCreateForImageBuffer` return code, and fall back to an individual allocation on pool failure, as forum developers suggest for Photo Booth ([Apple Developer Forums 726416](https://developer.apple.com/forums/thread/726416)).

If diagnostic 2 shows synchronizer drops, make the placeholder timing look like a camera's: one sender, PTS advancing by the frame duration from a single anchor rather than raw wall-clock reads, and nothing sent ahead of schedule. Then retest at 60 fps, as OBS ships, to see whether the client's pacing tolerance changes. If diagnostic 1 implicates effects, OffSight cannot switch them off from the extension. The right response is product-level: detect the condition in support flows, tell users which Control Center and Teams settings suppress the card, and design a placeholder that survives segmentation. Diagnostic 1's face-photo test will show whether a human-figure card does.

Independently, plan the format upgrade that Catalyst clients require. Publish 420v at 640×480, 1280×720 and 1920×1080 with one continuous frame-duration range, convert BGRA to the active format with VTPixelTransferSession, and keep the sink in BGRA ([kortexa-ai/aicamera #71](https://github.com/kortexa-ai/aicamera/issues/71)). Attach Rec. 709 colour tags after creation with `CVBufferSetAttachments`, since attribute dictionaries do not set them ([Apple Developer Forums 808137](https://developer.apple.com/forums/thread/808137)). Expose every format up front, because Apple DTS warns that changing streams at runtime causes `-50` errors and clients falling back to the FaceTime camera ([Apple Developer Forums 728019](https://developer.apple.com/forums/thread/728019)). Expect to restart registerassistantservice when rolling out an extension update. Treat this as compatibility hardening, not the expected cure for Photo Booth and Teams.

### Architectural alternatives if synthetic frames stay fragile

If the placeholder still cannot be made reliable, the fallback options form a ladder. The lightest is a looped clip with natural content in place of a flat card. CamLoop already ships this approach for "stepping away" ([Product Hunt: CamLoop](https://www.producthunt.com/p/camloop/camloop)), and it would also defeat a content-dependent failure. Deriving the card from live camera frames would work for the same reason, but it keeps the physical camera running and lights the privacy indicator, which defeats a shutter product's purpose. Alongside either, OffSight can add detection: OverSight listens on each camera's running-somewhere property and parses `com.apple.cmio` logs to find the using process ([OverSight AVMonitor.m](https://github.com/objective-see/OverSight/blob/master/Application/Application/AVMonitor.m)). That would let OffSight warn the user when an app opens the real camera instead of OffSight. For managed fleets, MDM privacy profiles can deny, but never grant, camera access per bundle ID ([Swif PPPC guide](https://help.swif.ai/en/articles/11103442-macos-privacy-preferences-pppc-policy)). No public macOS equivalent of Windows' privacy-shutter notification exists ([Microsoft Learn](https://learn.microsoft.com/en-sg/WINDOWS-HARDWARE/DRIVERS/stream/privacy-shutter-notification)), and DAL is off the table because it disables the privacy indicator. The virtual camera therefore remains the only approach found that keeps the meeting running behind a branded frame.

## Conclusion

The evidence moves the question away from "what format do Photo Booth and Teams want?" and towards "what do these clients do with a frame that QuickTime does not?" OffSight's own controls already answer the first question, because live frames succeed under the identical wrapper. Two consumer-side mechanisms remain: CMIO pacing, which is documented and drops frames silently by timestamp, and person-segmenting effects, which are plausible and would replace frames by content. Each predicts a different result from the effects-off test, the consumer log and the 2×2 swap. An hour of diagnostics should therefore replace weeks of format guesswork.

The research also shows that "works in QuickTime" is a weak acceptance test for a camera extension. QuickTime accepts formats that Catalyst rejects and tolerates timing that Photo Booth punishes. OffSight's test matrix should include Photo Booth, a Chromium WebRTC page, Teams and a Catalyst app. It should use a moving pattern, never flat grey, and a scripted AVFoundation client that reports drops. That matrix will catch the next regression before users do, whichever explanation this one turns out to have.
